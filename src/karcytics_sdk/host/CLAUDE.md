Hub-facing services — code here runs inside the Hub's process, not a plugin's.

- `core_services.py` — `CoreServicesServer`, a local loopback HTTP server the Hub starts once so *any* module process can reach core services (task scheduling, project I/O, diagnostics, theme queries) regardless of whether it was spawned in-process or isolated. Superset of the old spawn-time-pipe approach (`PluginUIDaemon`'s stdio, which is only 1:1 Hub<->that one module). Use this channel for small, infrequent control-plane calls only — bulk data (arrays, images, dataframes) should cross via the filesystem, same as project state.
- `qt_bridge.py` — `QtThreadBridge`: `CoreServicesServer` dispatches each RPC on a worker thread, never the Qt GUI thread. A handler that only emits a Qt signal is already thread-safe (Qt auto-queues signal→slot delivery), but anything that directly touches a widget must be marshaled onto the GUI thread through this bridge first.
- `trust_manager.py` / `trust_path.py` / `trust_storage.py` / `trust_overrides.py` — Ed25519 signature verification, split-manifest architecture, double-signing consensus ("Signing RBAC"). Security-sensitive: read `docs/internal/20_Security_and_Signing.md` and `21_Supply_Chain_Security.md` in the main `Karcytics` repo before changing verification logic, not just this module's own comments.
- `ai.py` — `AIServerManager`, the same "one local server, reachable over loopback" shape as `core_services.py`, predating it as the pattern's origin.
